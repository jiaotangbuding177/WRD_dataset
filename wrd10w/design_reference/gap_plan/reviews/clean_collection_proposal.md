# 干净原生闭环数据采集提案：先2条，核实后再4条和6条

日期：2026-10-30。本文只是可审查提案，不是执行授权或启动配置。本轮不调用Teacher／Actor／Judge，不加载模型权重、不训练、不改变原数据、设计、记忆或Git。建议当前仅审**2条路线、含预检最多24个原生会话、200个provider请求、6M输入+输出tokens**；后续4条、6条仅为条件式扩量方向，没有默认批准的全量预算。

## 要补的能力和当前事实

现有检查点07为552目标／150674监督tokens，其中436契约、116过程；原生自主A—D示范、训练准入的合格KEEP、独立dev/test实际数据仍为0。116过程不等于116条完整制作链。已有原文与局部正确动作应继续利用，但单纯再标注一批“下一步做什么”不足以补齐执行、修订和效用依据。

建议新增的主要单位是**真实原生闭环**：同一个controller在自己的原生会话中理解来源、选择路线、发现/读取资源、制作完整候选、主动要求真实消费与评价、读取实际返回、必要时修订及复试，最后自行作KEEP／REVISE／STOP。独立消费者和评价者可以是该controller经已核实的原生委派能力发起的其他原生会话；它们的工作区、条件和实际费用分别保留。

“一个原生controller自己闭环”不意味着一台模型独自宣判所有质量，也不意味着把多个外层启动的阶段拼接成一条原生轨迹。若原生环境没有可用的委派、隔离和回传能力，就不能宣称这种完整示范已可采集；先明确平台能力缺项，不能悄悄恢复外层逐步调度或自建Agent循环。

## 固定执行条件及必须先核的两件事

所有controller、消费者、独立Q统一使用镜像摘要 `sha256:97a0f55bec1ef293c15ddd5a17cc843050387bd2369dcf2fd388b1afd40810a2`、OpenClaw 2026.9.5、glm-5.3-flash、原生skills发现/读取/工具/会话循环，1800秒原生会话上限、每响应32768回复预算，6GiB／4CPU／1GiB shm。并行数只属于统一资源/预算管理，不能给不同组不同的工具或模型条件。首轮建议同时活跃原生容器不超过4；先核真实宿主容量，不把容器内存限额当作已分配内存或已证可并行数。

第一件事是原生自治是否真的可运行。读取实际原生工具发现结果和捕获schema，核对当前版本支持的原生委派与结果回传方式。历史53工具schema出现`sessions_spawn`／`agents_wait`不等于固定容器里能够实际调用。用公开小任务实测以下链：controller自行发起一个独立原生子会话，子会话在声明的相同环境/预算中执行，controller实际收到完整结果和产物身份，再自行决定下一步。另核消费者能否在隔离工作区只看到该case和声明的技能资源；无技能臂不得看见制作工作区中的技能。若考虑原生CLI fallback，必须是本机已存在并实测可用的原生会话启动方式，仍启动原生loop，不能写替代Agent循环，也不能由外层逐阶段派发。若做不到，明确自主采集的技术阻碍，停止企业演化采集，不用外层转发下一阶段任务来冒充通过。

第二件事是原始思考能否真实捕获。原生session里的thinking字段为空不证明供应方没有思考；反过来，也不能预设每条响应都有reasoning_content。预检保存实际provider请求/响应原字节、SSE块、response/request ID、结束状态、实际usage、原生消息/工具ID、实际system/tools捕获范围，检查是否真的存在可关联的原R，以及它如何对应当前响应。SDK未见前缀、缺失工具schema、partial响应、usage未知都单列，不能补造结束符或把新作者解释写成原R。

预检上限是**2个原生会话合计8个provider请求、0.3M输入+输出tokens、1小时经过墙钟**，计入首批总200请求/6M/6小时经过墙钟预算，可以用一个公开controller及其一个原生子会话共同完成上述检查。失败探针、原生CLI尝试和实际重试也占这2场/8请求，不另开免费恢复额度。这2场不是两条企业路线，也不计企业数据量。若原R不能真实捕获并关联原响应，**停止企业演化采集**，只保全已有探针/动作及具体技术缺项，不能静默转为动作-only后继续花满预算。后续发生原R捕获中断或归属断链，同样先停止新增演化、保全原件。捕获本身也不证明推理faithfulness或语义正确。

## 干净重建如何发生

每个制作controller仅获得该干净原会话、已核必要原附件、实际环境/权限与统一预算、可用原生技能资源及流程目标。不给旧混合来源route-card、previous_skill、旧maker输出或被保护反馈。不把受保护程序换个题面变成新训练程序。候选路线、资源、修订都由新的原生会话根据当前干净输入产生。

支持明确的新程序设计、代码制作和验证，不需要照搬旧受保护实现。原始输入缺件时，缺件判断和主动停止可以构成有效数据；但若本次主要目标是补完整构建，前置筛选应先保证大部分候选确有完整可用输入，避免又把整批算力花在问路径。

不要事先替controller列好每一步工具调用。给整体目标和事前固定的消费/评价合同，随后由模型自己选择读取、写程序、验证、委派、读结果、修订及结束。外层只投递冻结输入和资源、启动原生会话、记录轨迹/用量、管理统一硬预算，以及事后核验；不替模型自动执行skill、不向它补“现在该做C”等逐步提示、不篡改原生工具返回。

## 每条路线的完整消费与修订合同

每路线有2个不同消费来源的真实case，至少一个含该机制自然存在的字段、布局、编码、缺值或边界差异；不是偷偷给代码植入bug。case输入和检查条件在制作前冻结。

1. controller从制作来源出发做A/B，生成候选V0。程序、模板、资料及SKILL都有完整内容和版本身份，实际工具观察可证明写出，局部自测只是局部自测。
2. controller经实测可用的**原生委派**启动2个无技能消费和2个V0技能消费。四场使用相同case题面、附件、模型、环境、回复预算和原生发现机制，只改变预先声明的技能资源。实际技能发现、完整必要读取和资源执行要在原始轨迹中有证据；文件open或工具返回存在本身不证明模型已看到/理解全文。
3. 每case有1个独立Q会话，盲化两个输出的臂名称、随机顺序，只看该case要求、真实输入、实际产物及必要证据。Q不能看controller的自评或KEEP意愿。执行前先核对并冻结适用于本case的现行五维rubric、条目、权重和锚点，记录精确来源文件/行号及SHA；本提案没有证明某组历史权重已经适用于这批新case。缺少适用合同的部分应明确写成新评分提案，完成独立复核后再冻结，不能冒称旧合同。视觉条目要看真实像素。TSR和Q分别记录，UNKNOWN/UNSCORED不补零、不以成功乘Q。
4. controller自己读实际消费、Q和完整成本返回。如有具体可修问题，可在**最多一次资源修订**中生成V1。保留已送达失败对象、诊断、精确旧资源、补丁和新内容。若V0没有真实失败/不足，不为凑REVISE演示制造假失败。
5. 若有V1，两个case各做1场V1技能消费及1场独立Q。无技能基线只有在同题面/附件/环境仍完全相同、旧结果有效且成本完整时复用；Q盲比V1与原无技能结果。改变case、规则或依赖后不能继续复用旧对照。
6. controller自己作D：KEEP／REVISE但预算用尽／STOP／HOLD证据不足。事后审核判断它的理由是否正确，不因它写了KEEP就正向监督。

最大会话数的算术：1 controller＋2无技能＋2 V0技能＋2 V0盲Q＋2 V1技能＋2 V1盲Q＝**11个原生会话/路线**。无修订时7场。所有子会话都仍是原生Agent；外层不负责把上述阶段依次派出去。子会话发起、收到结果和后续资源版本的先后必须能从同一controller原会话取证，否则只算分阶段轨迹。

1800秒仍是每个原生会话的上限，不能为得到完整链偷偷延长controller。父会话等待/退出、子会话是否仍在运行及其终态均须记录；父超时不能凭外层完成后续Q或D补成同一条自主链。小任务仍来不及闭环时，完整性目标未达，应该调整下一批任务复杂度或提出另一个待审预算方案，不能回写本轮执行条件。

## 预算上限及计量规则

## 何时扩量，何时拒绝正向信用

预检通过后才做首2条。首2条至少要证明：真实原生controller能发起并实际接收独立消费和盲Q，能把返回绑定到同版本资源，能够在剩余时间内自己作有依据的收尾；原请求/响应/工具/版本/usage链可以复核。这是采集链是否可用的门槛，不要求一定产生KEEP。若只有外层阶段拼接或原R捕获缺项，应先解决对应缺口，不能靠加10条路线掩盖。

后续4条和6条按实际缺阶段/缺机制扩展；不能因为某条恰好KEEP就反复生成同质案例。若真实失败没有出现，可得到直接验证和收尾数据，但不能说已补修订分支；若12条没有合格KEEP，就明确正向封包链仍缺，不将最后文件或completed改标为成功。

建议把KEEP的事前探索性判据写清：2个发展case均真实交付，必须项通过；独立Q无已知重大错误、无相对无技能的实质退化；当前终版确实实际发现/读用资源；usage完整，终版边际消费成本有改善，且把制作/失败/修订/Q等固定成本纳入后，满足预先声明的复用情景。原226不得用于定阈值。Q未校准时只能称“按本批探索性rubric合格”，不能升级为论文金标准或总体收益显著。

例如可事前选定复用20次作为工程情景，同时公开N=1/5/20/100的敏感性，而不是事后挑有利摊销量。若平均无技能成本为c_N、终版技能消费为c_S、全部制作修订验证固定成本为C_fixed，则在c_N>c_S时报告盈亏平衡次数 `ceil(C_fixed/(c_N-c_S))`；否则没有有限回本次数。这个结果依赖当前case混合和成本稳定假设，不证明实际未来频率。每合格技能总成本按整批全部成功/失败/整理与采集成本除合格数，分母0时未定义；后续学生训练/部署费用另纳入相同口径，不用Teacher局部省token替代最终总成本。

正确的局部修复可以在最终STOP的链中获局部信用；错误诊断、无证据的原因和过宽结论即使最终交付也mask0。REVISE必须有真实已送达的失败或可核不足及明确改动，不能把无条件多跑一遍当作有效迭代。

## 交付与数据量如何计算

每条路线保留：所有原生会话全文及实际请求/响应，实际可捕获的原R，工具发现/读取/调用/返回，所有资源版本和完整内容，case输入与产物身份，真实失败与修订链，独立Q原件及复核，完整成本账，controller自己触发后续步骤的证据及最终D。未来结果只用于信用metadata，不倒灌先前输入。

**200个provider请求是算力预算，不能推断SFT target数。**上游请求、原生消息、包装请求与训练视图可能一对多或多对一；controller、消费者、Q的可监督响应和原R/动作数量，必须采集后按实际ID及原始字段对齐，并按canonical owner核算、去重及审查后才报告。本提案不以请求额度推导监督位置硬上限。两条完整自主链只是本批目标，不保证完成；最终可能为0。消费和Q轨迹单列，不能一律算为主沉淀能力；错误Q尤其不能因“独立”就转成gold。一个响应中的多个工具调用、原R/新理由、core/full视图及多个切窗都保留owner关系，不冒充新任务或新来源。

首批输入+输出上限6M是实际算力暴露，不是6M正监督tokens。16K/32K/条件长窗覆盖、原Rtokens、动作tokens、正向KEEP、有效局修、完整自主链和独立来源都按实际数组/原件分别报告；不能通过重复epoch或裁掉必要历史凑数量。

先2条、后续至多12条的方向是验证并补进当前缺失的真实因果闭环，**不是保证14B已经具备完整自主沉淀所需的足量主集**。只有闭环方法确实可采、多个机制有可监督构建/修订、出现可靠正反收尾，而且冻结的新dev/test可运行后，才据每条链实际有效标签密度与缺阶段设计下一批规模。若首批只新增浅层读取/计划文本，应明确未达到本提案目标，而不是又以一个包上传宣布充分。

## 与预期模型之间的可证伪关系

可见原生状态→真实正确工具行动，才支持模型学习何时执行；真实失败对象＋原诊断＋有效补丁＋同版本复测，才支持修订；独立消费/Q/全成本及正确D，才支持基于证据选择保留或停止；同一controller中实际发起与接收这些过程，才支持自主调度。分别缺失时，不能用别的阶段数量替代。

未来学生检验应在冻结新来源上比较base14B/SFT14B及base8B/SFT8B，统一原生环境、模型服务、工具、输入/权限和预算；检查完整链交付率、独立Q、修订后退化、错误归因、有效KEEP/STOP以及每合格技能全成本。只有比未训练基座更稳定完成这些任务，且包含失败/训练摊销后有实测收益，才能支持用户期望；采集成功、loss下降或新数据数量本身都不能提前证明。

本提案不改现有552数据和14B／8B计划，不自动把新采集预算写成运行中的任务。待实际执行另有明确范围后，再由根同步设计、执行冻结和记忆。
