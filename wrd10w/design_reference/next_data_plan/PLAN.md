## 六步处理顺序及实际交付

### 1. 补齐所有100个episode的真实依赖和版本时间线

将原会话、tool_call、实际返回、文件版本、路线卡、旧SKILL、测试输入和反馈producer连起来。补足for/head、exec内Python、变量路径、重定向、read_source分页及失败patch的部分副作用；以原实际观察核验，不能把文件存在或open等同于模型已读。

将共用producer按精确身份集中核一次，再把影响传播到相关事件；保护读取只隔离实际受影响后续，不借路径名字合并公共依赖。12个同路径后版本用已经找回的冻结SHA副本；缺原版本不拿最终文件冒充步前版本。81个新增保护ID保持不可回流。

每个缺口依次检查原载体、已定位同SHA副本、已发布Git/CAS对象；没有证据保留具体缺项并处理下一簇，不让一条断链阻塞整批。产物是可复核的event/resource/outcome表与实际原件，不只路径列表。

### 2. 对104种已有程序身份做去重后的代码／资源审查

先按真实原要求、完整依赖和接口审查整份程序；再核正常、边界、错误输入的现有测试证据。测试预期本身也检查，区分资源错误、坏测试、缺输入和执行环境问题。缺少复现时明确待验证；未经实际执行的验证不得写PASS，相关资源机械复现应单独列作有界验证，不重跑旧自建Agent循环。

整体有缺陷时保留有证据支持的局部推理／动作；需要独立函数资源或新功能委托时，完整提供其依赖、调用范围和作者身份。不能裁掉污染输入、删名字或复制后来正确代码，就声称旧过程已干净。保护来源派生代码不能靠重写任务描述洗为TRAIN。

交付每个候选的具体结论：可监督完整构建／可监督局部过程或修订／仍缺证／受保护／已证错误；对应全文、范围和证据均保全。

### 3. 整理真正带结果的诊断—修订—复测链

每链绑定：已送达原需求与失败观察 → 完整必要旧资源 → 原诊断及动作 → 实际新版本 → 同版本复测／消费 → 质量和费用结果。

信用分两层，所有层都挂实际结果：局部过程是否正确，以及最终技能是否合格、是否减负。正确修复不会因为后续成本过高而全归零；终态成功也不使错误诊断或误修自动获正loss。最终结果未知时，只能授已证明的局部信用，不授KEEP／整体成功。后验评估用于决定标签，不能放进先前动作的输入。

原生思考逐原字段／字符／SHA保留。累计R与逐turn R、新作者理由分别登记；不无标记拼接不相邻原句。合理探索或明确假设可以按其语义获信用，不要求它必须已执行，但不能把假设当事实或已验证结果。错误和未知部分仍在原文，mask0。

### 4. 补路线决策、控制和收尾标签

从已经核清的真实状态标注：何时继续读源、复用／新建、查依赖、写程序、验证、定位错误、局修、复测、停止或保留。新作者标注与原Teacher原文分开；对旧工具ABI的新原生表达明确条件变化，不冒充历史调用。

可以基于明确事实补显式调度决策样本，不能靠标注制造不存在的自主执行记录、工具返回或合格KEEP。真实多阶段串接、局部闭环、合成／重构状态、单native自主完整链四类分报。多次外层派发的日志不拼成模型自发调度演示。

若原始材料没有干净的正向保留链或单native自主示范，整理报告明确缺口及所需新数据合同；本计划不自动启动新Teacher采集或原生业务实验。原有固定OpenClaw发现／读取／工具和会话循环保持，不自建替代Agent循环。
