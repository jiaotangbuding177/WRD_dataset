# WRD全流程蒸馏：一手研究依据与训练算法建议

调研日期：2026-10-25。仅方案，未训练、未发教师/Actor/Judge调用、未访问企业正文。本文不声称文献中的收益已在WRD成立。具体可用样本数以本项目全链路盘点及准入清单为准。

## 训练对象

蒸馏的是可观察的决策策略：给定当前会话证据、已有路线/技能/资源版本与已发生的工具反馈，选择下一阶段、下一动作、修订范围及停止条件，并形成可复用技能。保留原生OpenClaw的工具发现/读取/调用和会话循环；不能用离线数据脚本替代Agent。

可训练的“思考”包括日志已经显式输出的分析、路线比较、资源选择理由、测试解释和修订理由。补充标注应为有证据引用的简洁决策摘要，单独标为derived_annotation，不冒充教师原始推理。未记录的内部隐藏CoT、教师logits及真实反事实结果不可恢复。输出有用决策依据并证明其行为效果，比追求长篇思考文本更可检验。

## 一手证据表

| 来源 | 支持的设计 | 不能直接外推的结论 |
|---|---|---|
| [Distilling Step-by-Step, ACL 2023](https://arxiv.org/abs/2305.02301) | 在标签之外，把教师给出的理由作为额外监督，采用多任务学习。WRD可分开监督决策、证据摘要与行动。 | 四项NLP基准的结果不证明长企业工作流可无损压入14B；生成理由不自动等于忠实原始思考。 |
| [AgentTuning](https://arxiv.org/abs/2310.12823) | 以高质量交互轨迹学习Agent行为，并混合一般指令。训练单位应包含动作前状态及反馈。 | 不支持把数万动作都当独立任务，也不保证只学工具语法就会掌握WRD筛选与评价。 |
| [CodeAct, ICML 2024](https://arxiv.org/abs/2402.01030) | 多轮执行、观察与动作修订可作为学习材料；不能仅保留最终回答。 | 本项目不因此改用CodeAct工具协议或Python执行器，仍保持既有OpenClaw协议。 |
| [STaR, 2022](https://arxiv.org/abs/2203.14465) | 正确结果与对应理由经筛选后迭代训练，说明“理由＋结果”值得联合监督。 | WRD没有数学标准答案；给定终局反向编造早期理由会产生后见泄漏。当前不运行自生成循环。 |
| [ReST, 2023](https://arxiv.org/abs/2308.08998) / [ReST-EM](https://arxiv.org/abs/2312.06585) | 生成、独立反馈筛选、离线再训练能够复用昂贵样本；可作为后续有界策略改进的依据。 | 仅整理历史日志不是已实现ReST/RL；只收留存赢家会丢弃正确拒绝与真实修复轨迹。 |
| [Let's Verify Step by Step](https://arxiv.org/abs/2305.20050) | 对中间步骤提供反馈，与只看结局不同。WRD应标注证据支持性、资源正确性与停止决策，而非整场成功则每步全对。 | 数学过程监督结果不等于WRD已存在可靠过程奖励。不能把自动规则通过当人工gold。 |
| [SCoRe, ICLR 2025](https://arxiv.org/abs/2409.12917) | 指出离线修订轨迹SFT可能因错误分布不匹配或行为坍缩而不足；未来必须测试学生自身错误上的纠错。 | 不应承诺训练后自动自我进化；当前不启动在线RL，不用教师错误分布上的分数替代学生闭环结果。 |
| [DPO, NeurIPS 2023](https://arxiv.org/abs/2305.18290) | 相同条件输入的chosen/rejected偏好优化可避免在线采样；适用于证据充分的决策分歧。 | 不同任务、不同资源状态、收到新反馈前后的输出不能未经对齐拼成偏好对。无技能/有技能Actor两臂也不是相同输入。 |
| [Qwen3技术报告](https://arxiv.org/abs/2505.09388) / [14B官方卡](https://huggingface.co/Qwen/Qwen3-14B) | 同系列支持thinking/non-thinking与工具交互；14B/8B作为主对照可减少基座家族差异。14B官方卡标原生32768总tokens，YaRN为扩展方案。 | 模型原生长度不证明Spark上该长度训练已可用；不因当前有更新家族就静默更换已固定基座。 |

## 建议的一条主训练路线

以下比例/参数为待验证的起始建议，不是文献最佳值或已实测结论。使用同一14B/8B数据ID、mask、来源拆分、曝光计划和输出预算。

1. **过程SFT**：按路线筛选、任务准备、资源制作、反馈解释/修订、封装停止五类均衡采样。建议先用4K/8K完整阶段窗口学习格式与基本决策，再转16K/32K学习依赖；不把超长轨迹硬截成丢失前因的目标。每条训练记录保留task/episode/revision/parent/工具反馈位置等关系。
2. **反馈条件下的修订SFT**：输入真实旧版本＋真实失败/评审反馈，目标为后续得到验证的修订及理由。错误步骤保留为已观察上下文，其错误输出loss=0；不要把修复后版本倒灌到修复前历史。成功初版与正确停止/拒绝继续混入，防止模型见到任何反馈都过度改写。
3. **有条件的偏好训练**：仅当盘点得到同状态、同预算、同资源的可靠偏好对，才考虑短程DPO；否则主方案到SFT结束，不能为配齐算法名伪造负例。保守起点beta=0.1、LR=5e-6、最多一遍、保留SFT锚点；具体库版本/实现需另锁定。比较资源成本前先满足正确性和交付质量。
4. **后续才考虑学生闭环改进**：未来另获运行授权后，以固定原生环境在训练来源上收集学生失败→真实反馈→修正轨迹，独立验证后做一轮ReST式再训练；所有失败/采样/评审成本入账，开发/盲测及正式226/250不进入此循环。

### 可执行的损失定义

令s为阶段，i为同阶段示范，t为目标token。a_it=1仅标在被准入的assistant输出（可见理由/决策/动作/资源内容），系统、用户、工具返回、未审目标及已知错误动作均为0：

`L_stage = mean_s mean_i [ -sum_t a_it log p_theta(y_it | h_it) / max(1,sum_t a_it) ]`

第一版建议每个非空阶段相同总权重，避免read/exec长轨迹占尽loss。阶段内先按独立路线/来源均衡，再抽记录；不因一条长链被拆多窗而放大其总权重。置信分层先用显式纳入/排除和分层报告，不让未经校准的LLM分数直接充当连续奖励。

对于相同前缀h的偏好对，仅对assistant continuation计算：

`L_DPO = -log sigmoid(beta * [log pi_theta(y+|h) - log pi_ref(y+|h) - log pi_theta(y-|h) + log pi_ref(y-|h)])`

若y+依赖y-未获得的新反馈，必须先把两者都放到相同反馈状态下重新比较，否则不是合法同状态偏好对。后者可以做修订SFT，不能直接做DPO。

“证据→决策→行动”的标注可训练为另一个短prompt-completion视图。它与原轨迹共享parent_id与总采样预算，不能重复计入独立样本量。先验标签如“调用read”可机械恢复，语义如“该路线应淘汰”必须有真实条件/结果及审阅支持。对未知项保留unknown。

### 完整轨迹与长上下文

完整阶段在长度容许时一次送入，所有准入assistant轮次可有loss；非正例动作可作masked历史。跨阶段多会话通过结构化中间状态衔接，不强行伪装为原本不存在的一条原生会话。超过32K的记录保持完整归档，再制作有来源定位的检索/状态摘要视图；摘要本身也需审核，统计为派生视图而非新增独立任务。

同一assistant目标在重叠窗口只计算一次loss。官方模板可能在历史轮次省略thinking字段，不能假定消息JSON中的可见分析已进入训练；必须检查最终token序列、reasoning_content渲染、工具边界与逐段mask。当前前缀异常须单列，不用字符长度强行修复。

## Spark可行性与实现依据

[NVIDIA官方Spark PyTorch微调playbook](https://github.com/NVIDIA/dgx-spark-playbooks/blob/main/nvidia/playbook-pytorch-fine-tune/README.md)列出DGX Spark统一内存平台、LoRA/QLoRA及PyTorch容器方案。该文当前参考镜像为25.11-py3并列出一组HF依赖；这是兼容候选，不是本机已验证环境。旧build.nvidia.com/spark/pytorch-fine-tune/instructions链接本轮打开重定向到PEFT首页，故以实际仓库原文为依据，不把失效跳转当实验验证。

建议主起点BF16 LoRA：r32、alpha64、dropout0.05，attention和MLP线性层；AdamW LR1e-4、warmup3%、clip1、microbatch1、有效batch16，gradient_checkpointing，use_cache=false。14B/8B顺序训练、不并驻；32K先有界测峰值内存/吞吐/CPU fallback，不能因121GiB统一内存便假定32K稳定。14.8B BF16权重约27.6GiB，之外还需激活、梯度、优化器、工作区和系统内存。统一内存不能视为独占GPU显存。QLoRA作为显存/内存压力下备选，要额外验证ARM64/GB10量化内核；不把FP4推理峰值或桌面显卡tok/s拿来报训练速度。

[TRL SFT官方文档](https://huggingface.co/docs/trl/sft_trainer)支持assistant-only与completion-only监督，但模板生成块及具体版本决定mask行为；必须做逐token核验，当前文档不能替代已锁旧版本的实现检查。[TRL DPO官方文档](https://huggingface.co/docs/trl/dpo_trainer)给出prompt/chosen/rejected格式，支持预计算参考log概率以减少同时驻留模型；该预计算仍是GPU工作，应待授权后执行。文档随版本变化，正式运行前锁软件/镜像digest并验证，当前不安装。

## 必须用实验回答的假设

- 相同独立来源与监督token曝光下，阶段均衡＋决策依据是否优于只学工具动作或最终技能文件？
- 真实反馈条件的修订训练是否提升学生自身失败的修复率，同时不增加无必要修改和错误保留？
- 模型能否根据实际质量/成本证据选择retain/revise/reject/defer，并保持证据引用正确？
- 14B相对8B是否提高合格技能交付数，且包含训练摊销、所有失败/修订/评审/回退后每个合格技能总成本更低？
- 不带理由、带简短证据摘要、带原始可见分析三种视图，在同一来源划分/输出预算下质量与Token成本如何变化？

不能承诺“原pipeline成功则蒸馏学生必然成功”。保留pipeline作为运行与评估结构，让学生逐步替换其中模型职责；最终以新来源上交付成功率、独立五维Q、资源复现、适用边界、修订与停止决策和每合格技能全成本判定是否达到替代条件。
